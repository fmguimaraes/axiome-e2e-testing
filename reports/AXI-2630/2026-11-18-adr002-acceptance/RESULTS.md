## Defects found (confirmed, backend — out of this story's ownership)

### 1. `CandidatesService.replaceAutoGeneratedSpecs` race — consolidation never completes (BLOCKING for AC3)

- **Location:** `axiome-back/apps/organization-service/src/candidates/candidates.service.ts:981`.
- **Symptom in logs** (`docker logs axiome-w5val-backend`), firing at the exact timestamp of
  this story's own dataset ingestion (`06:57:39.218...Z`, matching dataset upload
  `06:57:38`):
  ```
  Unique constraint failed on the fields: (`dataview_spec_id`)
      at async CandidatesService.replaceAutoGeneratedSpecs (main.js:17208:9)
  ```
  — an uncaught error inside a delete-then-insert transaction (`tx.dataviewSpec.createMany`),
  consistent with a concurrent-request race (matches the pre-existing AXI-2635 note:
  "stuck-running state, cross-process race"), aggravated by concurrent agent load on the
  shared stack tonight.
- **Confirmed, quantified, live** via direct SQL against the demo Postgres
  (`axiome-localhost` container, schema `organization_svc`):
  ```sql
  SELECT count(*) total,
         count(*) FILTER (WHERE latest_consolidated_node_id IS NOT NULL) has_node
  FROM organization_svc.view_analyses WHERE created_at > now() - interval '24 hours';
  --  total | has_node
  --    150 |        0
  ```
  **0 of 150** `view_analyses` created in the last 24h ever reached a consolidated node.
- **Effect on AC3:** the result page itself, the "Add a chart" entry, and the chart editor's
  Template dropdown all render correctly (confirmed via screenshot — workspace/project context
  resolves correctly after fixing an unrelated `ORG` constant mismatch in this spec). The
  editor's Y/Group **column-binding `<select>`s never populate any options**, even though the
  underlying column profile data is independently confirmed correct and ready via direct API
  calls (`GET /workspaces/:ws/datasets/:ds/profiles/:id/columns` returns `col_pct`, `col_group`
  etc. with `status: "ready"`). The empty selects co-occur with, and are plausibly caused by,
  the unconsolidated state above; root cause was not isolated further inside this story's
  ownership boundary (front/test code), and should not be worked around by retrying — per the
  coordinator's own instruction, reported as blocking.
- **Not fixed by this story** (app/backend code is out of scope for an e2e-testing story).
  Recommend filing a new Jira ticket against the backend owner; I did not file one as this
  session has no Jira write access configured for me to verify against the live board.

## Known limitation — AC25/AC29 "shape" is template-id, not rendered pixels/DOM

The coordinator asked that AC25/AC26/AC29 assert the rendered **shape** (points/box/badge/
brackets), not just evidence existence. What is implemented asserts the chart's own
`templateId` matches a regex naming the box/strip/jitter/Dunn/Kruskal template family, read
from `GET /workspaces/:ws/datasets/:ds/candidates/:chartArtifactId` — a step up from "evidence
exists" (the previous state), but still not a DOM/rendered-payload assertion of panel count,
shared axis, or bracket placement. No chart-shape/DOM introspection route or Playwright
selector set for this was identified within budget. AC26 in particular (3 panels, shared axis,
brackets vs reference only) needs this and was not reachable at all (see AC26 row above).
