## Update 4 — AXI-2653 live, AC3 re-run: still fails, real root cause found (front-end, diagnosis only)

AXI-2653 (the `replaceAutoGeneratedSpecs` race fix) is merged and live on w5val (back main
`83375f2a`). Re-ran `AXI-2647.3` once, `API_BASE_URL=http://localhost:3001` exported
explicitly. **Result: still fails, identically** — same timeout on
`slot('Y').selectOption({ value: 'col_pct' })`, "did not find some options", 582 retries,
5.2m (`run24-full.log`). This confirms AXI-2653 fixed a real but **separate** defect and did
**not** cause or fix this symptom — the earlier causal claim in Defect #1 below was wrong and
has been struck through. Per instruction, not retried a second time; traced instead (code
reading only, no app code changed):

- The failure screenshot's toolbar shows **"Statistical result: stats.dunn_p_..."** as the
  currently *selected* snapshot (a Dunn rule-derived result), not the base ingested dataset.
- `axiome-front/src/pages/ProjectViewAnalysisDetail.tsx:2769` —
  `const effectiveDatasetId = resolveChartTargetDatasetId(currentSnapshot, viewAnalysis);`
  and `:3487` — `<VisualizationEditor datasetId={effectiveDatasetId} ... />` — the editor is
  authored against whichever dataset is *currently showing*, including a rule-derived result.
- `axiome-front/src/pages/viewAnalysisSlice.helpers.ts:267-272` —
  `resolveChartTargetDatasetId` returns `currentSnapshot?.datasetId ?? viewAnalysis.datasetId`
  — since a statistical result is selected, it returns that derived result's own dataset-version
  id, not the base CSV dataset this story's test uploaded/profiled.
- `axiome-front/src/components/VisualizationEditor.tsx:163-177` (`loadInitialData`) calls
  `profilingApi.fetchProfiles(workspaceId, datasetId)` with that derived id. Rule-derived/
  statistical-result dataset versions are never profiled (profiling only runs on ingested
  datasets via the ingestion pipeline).
- `VisualizationEditor.tsx:187-199` (`loadColumnsFromProfiles`): `if (profiles.length === 0)
  return;` — with zero profiles for that id, `columns` (initialized `[]`) is never populated,
  so every binding `<select>` renders with zero options. This matches the symptom exactly and
  is independent of the consolidation race.

This also explains why the test's own earlier profiling-readiness poll always passed without
fixing anything: it polled the status of the story's own uploaded *base* dataset's profile,
not the derived dataset the editor was actually reading.

**Not a story-attributable fix** — front-end behavior, out of this e2e-testing story's
ownership. Recommend filing against the front-end owner: either `VisualizationEditor` should
fall back to the analysis's base dataset when the selected snapshot has no profile, or
`resolveChartTargetDatasetId` should prefer the base dataset for chart-authoring purposes.

- **Symptom in logs** (`docker logs axiome-w5val-backend`), firing at the exact timestamp of
  this story's own dataset ingestion (`06:57:39.218...Z`, matching dataset upload
  `06:57:38`):
  ```
  Unique constraint failed on the fields: (`dataview_spec_id`)
      at async CandidatesService.replaceAutoGeneratedSpecs (main.js:17208:9)
  ```
  — an uncaught error inside a delete-then-insert transaction (`tx.dataviewSpec.createMany`),
  consistent with a concurrent-request race (matches the pre-existing AXI-2635 note:
  "stuck-running state, cross-process race"), aggravated by concurrent agent load on the
  shared stack tonight. **Real, confirmed, separate defect — now fixed by AXI-2653 (back main
  `83375f2a`).**
- **Correction (coordinator, 2026-11-18):** the `latest_consolidated_node_id` 0/150 figure
  below was WRONGLY attributed to this race in the previous version of this report. That field
  is set only by the unrelated cross-dataset merge feature (`merge-run.service.ts`
  `completeMerge`) and has no causal link to `replaceAutoGeneratedSpecs` or to AC3's empty
  column selects. Kept here only as a now-corrected historical note — do not cite it as evidence

         count(*) FILTER (WHERE latest_consolidated_node_id IS NOT NULL) has_node

## Known limitation — AC25/AC29 "shape" is template-id, not rendered pixels/DOM

The coordinator asked that AC25/AC26/AC29 assert the rendered **shape** (points/box/badge/
brackets), not just evidence existence. What is implemented asserts the chart's own
`templateId` matches a regex naming the box/strip/jitter/Dunn/Kruskal template family, read
from `GET /workspaces/:ws/datasets/:ds/candidates/:chartArtifactId` — a step up from "evidence
exists" (the previous state), but still not a DOM/rendered-payload assertion of panel count,
shared axis, or bracket placement. No chart-shape/DOM introspection route or Playwright
selector set for this was identified within budget. AC26 in particular (3 panels, shared axis,
brackets vs reference only) needs this and was not reachable at all (see AC26 row above).
